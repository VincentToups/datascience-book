Javascript
==========

We will start by thinking of Javascript as just a regular old programming language. 
It is not all that dissimilar to R.

Basic stuff that should be very familiar to an R programmer:

Types:
------

1. numbers (floating point, integers, flexible)
2. strings (denoted with single or double quotes or using "templates" which perform substitution)
3. arrays: ordered collections denoted with [] and indexed with [] (not everything is an array in JS so we just need [])
4. objects: collections of named/value pairs denoted with {} and indexed with [] or `.`
5. functions (but actually they are methods): strangely enough, denoted with the `function` keyword
6. arrow functions (actual functions): denoted with an arrow like this x => x + 1
7. documents/elements: things representing the HTML page or the elements thereof
8. boolean expressions: denoted `true` and `false`
9. various sorts of undefined things: `undefined` and `null`

As with most stuff in most programming languages these are all somewhat more complicated than they need to be
because they were designed by midwits over the couse of a decades.

Variables
---------

Variables are bound in one of a few ways. 

1. `var` expressions: `var x` (declares but doesn't bind), `var x = 10` (creates a binding in the current scope).
2. `let` expressions: similar to var but better behaved with respect to scopes. `var` binds at function scope but `let` has a bit 
   more granularity: binding at block scope. 
3. `const` like `var` but creates an immutable *binding*. The value connected to the constant might change (eg, if its an array you might add or remove elements) but you cannot point the variable to another value.

Why so many different ways to bind variables? The dragon of history, in whose jaws we are all gripped: `var` was originaly the only
way of binding variables (except for functions) but it had some weird behavior:

``` js demo
if(Math.random()<0.5){
    var x = 10
} else {
    var y = 11
}
console.log(x,y)

```
Even though we use var in two different legs of the if statement, it introduces bindings for both variables 
and one is just set to undefined. This may be the desired behavior but not the non-locality of it. Note that 
usually when we mention a variable, JS will try to find it and if it can't then its an error. Note that that 
is different from the variable being bound to undefined.

Thus eventually `let` variables were created, allowing block scope variables. This allows a user to specifically indicate (by using `let`)
that a variable is meant to be confined to a specific block rather than bound at the function scope.

Note that the semantics of variable lookup are the same as in R: we look in the current scope, then up *lexically* until we find
a binding and if none exists we give up and raise an error. Note that unlike in R, where we don't have an expression per se
indicating the creation of a binding, the single equal assignment operator can be more reasonable: it just *mutates* a binding 
when it finds one in whatever scope. Sadly, however, forgetting to put a var or a const or a let in front will just create a "global" binding
of a sort. This is now widely understood to be undesireable so you can turn off this behavior with a so-called "pragma":

``` js demo
"use strict";
x = 10
```
Anyway, as in many languages (not R) declaring functions is done via syntactic sugar:

``` js demo
function returnHello(){
    return "Hello"
}
console.log(returnHello())
```

Note that this is equivalent to:

``` js demo
var returnHello = function(){
    return "Hello"
}
console.log(returnHello())
```

Or nearly so: `function <name>` definitions are always callable anywhere in the scope. When you bind using a `var` expression then the semantics are as above: the binding is created but not initialized unless a code path does so.
`const` has similar behavior to `var`. You can bind functions with `let` as well, to get that behavior.

Note that functions must `return` their values and, in general, JS is less expression oriented than R. `if` and other similar
statements do not evaluate to anything meaningful, instead you must side effect appropriately. A real hassle, if you ask me.

No way to avoid it: there are other function like objects in JS:

``` js demo
let returnHello = () => "Hello"
console.log(returnHello())
```
To explain this we need to fully appreciate the way object oriented programming in JS works, which we will talk about in a second.

But just to finish things up:

``` js demo
let x = 5;

// if / else if / else
if (x > 10) console.log("big");
else if (x > 0) console.log("small");
else console.log("negative");

if (x > 10) { 
  console.log("big");
} else if (x > 0) {
  console.log("small");
} else {
  console.log("negative");
}
// for loop
for (let i = 0; i < 3; i++) console.log(i);

// while loop
let n = 0;
while (n < 3) {
  console.log(n);
  n++;
}

// conditional (ternary) expression
let msg = x > 0 ? "positive" : "non-positive";
console.log(msg);

```
Note that you may leave out the block syntax `{}` for these expression legs if the leg is a single expression.
