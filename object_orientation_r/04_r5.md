# R5

In most programming languages with OOP you will see a system that resembles
R5. These systems are nearly ubiquitous and so its worth understanding them
even if we don't see R5 classes all that often in R.

In a "traditional" object system like R5 methods are associated directly with
*one* class and defined with that class.

``` R file=eg_R5.R start=1 end=53 session=eg_R5

```
With this in hand we can reproduce the first part of our S4 code.

``` R capture session=eg_R5
fido  <- Dog$new(name = "Fido")
milo  <- Cat$new(name = "Milo")
todd  <- Fox$new(name = "Todd")
shep  <- BorderCollie$new(name = "Shep")
buddy <- Labrador$new(name = "Buddy")
seamus<- IrishSetter$new(name = "Seamus")
bob   <- Person$new(name = "Bob")

fido$make_sound()    # "Woof!"
milo$make_sound()    # "Meow!"
todd$make_sound()    # "Yip!"
shep$make_sound()    # "Ruff!"
buddy$make_sound()   # "Woof!"
seamus$make_sound()  # "Woof!"
bob$make_sound()     # "Bob"

```
Note that we do not call methods on functions in this world. We invoke methods
from objects via the `$` syntax:

```
fido$make_sound()
```

And something complicated is going on here: `make_sound` is resolved by looking
not at the object itself, but its class hierarchy, searching in order until
an appropriately named method is found.

This has the disadvantage that we need a bit more boilerplate to use our objects
in a functional way:

``` R capture session=eg_R5
Map(function(x) x$make_sound(), list(fido, milo, todd))
```
Mutability
==========

Like many things, R has a bit of an idiosyncratic approach to what we call mutability.

We've only programmed in R in this course so far so we might not have even noticed it.

But consider:

``` R capture
library(tidyverse)

data <- tibble(x=1:20)

add_y <- function(df){
    df %>% mutate(y=x+10)
}

add_y(data)

print(data)
```
That is to say that even though we mutated the data frame in the function add_y, those changes do not actually change the data frame. Even if we write the code like this:

``` R capture
library(tidyverse)

data <- tibble(x=1:20)

add_y <- function(df){
    df$y <- df$x + 10
    df
}

add_y(data)

print(data)
```
The changes do not actually change the outer data frame.

R favors immutability, and the slots in S3 behave in roughly this way as well. This is wise, in my opinion, but the overwhelming
convention in languages is that objects should be mutable, and that if we modify an object in a function or something like that
the changes should be reflected everywhere.

This is how R5 behaves.

``` R capture session=eg_R5

rename_thing <- function(x, to){
    x$name <- to
}

rename_thing(fido,"Odif")
fido

```
Give the people what they want, I guess. Note that this kind of behavior allows non-local side-effects. Anyone who gets a hold of an instance of a class in this system can change its values. This is one of those situations where the simple thing you think you want is wrong.
